AirPrinter

Share Windows printer queues on your local network. AirPrinter discovers them with DNS-SD, receives jobs over IPP, and routes each job to its selected queue.

01 / Overview

Project overview

This document describes the direct-printer-broadcast branch. AirPrinter is a Tauri desktop app for Windows 10 and 11 that can share installed Windows printer queues individually. Apple clients discover a shared queue over mDNS and send jobs over IPP/HTTP for processing by its Windows driver.

01

Independent queue sharing

Share multiple Windows queues independently. Each queue has its own /ipp/print/<id> resource path and discovery identity.

02

Lightweight background operation

Closing the window unloads the WebView while printer sharing continues. Queue status is checked every 30 seconds in the foreground and every 5 minutes in the background.

02 / Getting started

Getting started

1

Set up a Windows printer

Install its driver and confirm that a local Windows test page prints successfully. USB, network, and paired queues are supported. Interactive virtual destinations such as PDF, XPS, OneNote, and Fax are not shown as physical printers.

2

Share the queues you need

Enable each physical queue in the app. If Windows Firewall blocks access, enable the local network rule.

3

Connect to the same local network

The PC can use Ethernet while an iPhone, iPad, or Mac uses Wi-Fi through the same router. Devices must be able to communicate; guest networks and AP isolation block discovery.

4

Select the queue in the system print dialog

Open the system print dialog in an app that supports printing on your Apple device, then select the shared queue. Stopping one queue does not affect another.

Validation status

The direct-broadcast implementation has successfully completed real-device Apple system printing and produced a physical print. More OS versions, document formats, and print options still need validation. See the conformance plan for known gaps.

03 / Architecture

How it works

Choose a shared queue in the phone's system print dialog, set options, and tap Print. The PC receives and renders the job, then sends it to that queue. Everyday printing does not require downloading a document, opening a viewer, or confirming again on the PC; the browser test page is only for connection diagnostics.

STEP 01Detect queuesWindows drivers and capabilities
STEP 02Advertise servicesmDNS / DNS-SD
STEP 03Receive jobsIPP over HTTP
STEP 04Render pagesPDF / JPEG / raster
STEP 05Send to the driverGDI / Windows Spooler
Job status

IPP first returns a pending state; the job can later be queried or canceled. A job leaving the Windows queue only confirms that the queue stage finished; it does not by itself confirm physical output.

04 / Protocol

Protocols and document formats

StageImplementationDetails
Local discoveryPer queue: _ipp._tcp, _universal._sub._ipp._tcp, _printer._tcp_printer._tcp uses port 0. See the conformance plan for pending subtype and LOC work.
TransportIPP/HTTP, with a per-queue path /ipp/print/<id>Supports Print-Job, Validate-Job, Create-Job, single-document Send-Document, Get-Job-Attributes, Get-Jobs, and Cancel-Job. The path binds each job to its Windows queue.
Document formatsPDF, JPEG, URF, PWG RasterPDF uses the Windows PDF API. Images and advertised raster formats are rendered and sent to the driver through GDI.
Print optionsJob name, color, duplex, copies, media size, quality, orientation, page range, scalingPage numbers refer to the received document. Scaling supports fit, fill, actual size, and automatic modes. Other options follow Windows driver capabilities; unsupported values are rejected.

IPP port 631 is preferred. If it is occupied, an available port from 8631–8699 is used and advertised through DNS-SD. An ipp:// URI may omit the default port 631; the HTTP Host header must still match the connection port.

Compatibility

The direct-broadcast implementation has completed a real-device Apple print, but the project has not passed full IPP Everywhere 1.1 conformance. It does not currently advertise _print._sub._ipp._tcp or claim support for every standards extension. URF is a document format for client interoperability; discovery and transport still use DNS-SD and IPP.

05 / Network

Network and security

Ports that must be reachable

  • UDP 5353: mDNS discovery
  • TCP 631: preferred IPP port
  • TCP 8631–8699: fallback range when 631 is occupied

Ethernet and Wi-Fi can connect through the same router. Device-to-device communication and multicast must be allowed.

Explicit network access

“Allow local network access” triggers a Windows administrator prompt. Once approved, the rule applies only to the AirPrinter executable and local subnet across Windows Private/Public network profiles.

The IPP endpoint has no authentication. Enable sharing only on a trusted local network.

Manual alternative in an administrator PowerShell session

.\scripts\enable_firewall.ps1 -Program (Resolve-Path .\src-tauri\target\debug\airprinter.exe)

For an installed build, replace the EXE path with its actual location. Opening this HTML document does not change network or firewall settings.

06 / Build

Development and builds

The frontend uses TypeScript, Vite, Tailwind CSS, and DaisyUI. The backend uses Rust, Tauri 2, mdns-sd, tiny_http, and ipp. Windows printing uses installed printer drivers and system PDF/image APIs.

Run from the project root

pnpm install
pnpm tauri dev
pnpm tauri build

Run pnpm build to build only the frontend. If a newer pnpm version rejects the local dependency directory, use pnpm --config.verify-deps-before-run=false run build.

07 / Validation

Validation and current limitations

Local validation

Existing Rust tests cover independent queues, routing, and virtual-queue output. See the current review record for test results for the latest changes.

Real-device coverage

Direct broadcasting has completed a real Apple system print and produced a physical print. More OS versions, formats, duplex settings, copies, media sizes, and error states still need validation.

Receive-only diagnostic mode

Use airprinter.exe --receive-only "absolute path" to save received documents as pending jobs without calling the printer driver. This mode is only for diagnosing job reception. Normal mode processes and routes jobs automatically; users do not need to download documents or print them manually.

Protocol and local print simulation

cargo test --manifest-path src-tauri/Cargo.toml --locked
cargo test --manifest-path src-tauri/Cargo.toml --locked -- --include-ignored --nocapture
python scripts/diagnose_mdns.py --self-test

Standalone Node.js client simulation

cargo build --manifest-path src-tauri/Cargo.toml --example simulate_lan --locked
node scripts/simulate_airprint.mjs 172.22.48.1

Replace the IP in the JavaScript command with the host-only virtual adapter address on your machine. This computer's Hyper-V default switch does not loop back mDNS multicast, so the script labels the DNS-SD portion as an isolated UDP simulation. IPP requests still reach the real Rust service and do not submit jobs to a fictitious queue.

Check live broadcasts from another device

python scripts/diagnose_mdns.py --seconds 8

Resource limits: 64 MiB per upload, 512 MiB total raster decoding, 500 pages, 120 seconds per Windows submission, 4 jobs processing concurrently, and 32 unfinished jobs.
